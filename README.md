# moxml-testsuite

Reference tests for the moxml processing model: the language-neutral,
engine-neutral conformance dataset every moxml implementation (the Ruby
reference, moxml-rs, moxml-ts, ...) must pass.

## Layout

- `tests/moxml-conformance.json` - the dataset: committed model answers
  as data, schema-versioned (`schema` records the row-shape revision,
  `generator` the exporting moxml release). Seven families:
  builtin lexical spaces, XSD pattern translation, namespace wildcards,
  the entity registry, serialization shapes, C14N vectors, and XSD
  structural validation.
- `tests/data-plane-rows.json` - the element-rows contract dataset
  (processing-model § The data plane): canonical XML documents and the
  exact row tuples. Its reference implementation is moxml-rs
  (`cargo run --bin export_rows`), distinct from the model answers'
  exporter - the two datasets version separately.
- `schema/test.schema.json`, `schema/data-plane-rows.schema.json` -
  JSON Schema (2020-12) for every row.
- `tools/` - gem-free validators and the corpus bridge.

## Contract rules

1. Language independence: no implementation class names or engine
   identifiers anywhere in the data. Each implementation maps its native
   errors onto its own surface - the dataset only commits ANSWERS.
2. Rows pin SHAPES, not only answers: the row tuples the cross-language
   runners compare (columns, order, encoding) are part of the contract.
3. MECE: each committed answer appears exactly once; id-carrying
   families have unique ids; the family set is closed
   (undeclared families fail validation).
4. Completeness: nothing invented, nothing dropped - the dataset is
   regenerated from the reference implementation's case tables, and the
   identity gate proves the copy here matches that export on every run.

## Tooling

Generation lives in the reference implementation (lutaml/moxml):
`rake conformance:export` distills the case tables into the dataset.
Data changes land here via PR, regenerated from the reference - never
hand-edited without regeneration parity:

    rake corpus:regen        # regenerate tests/ from the moxml checkout (MOXML_PATH)
    rake corpus:check        # fail if the dataset drifts from the reference

## Validation

The corpus validates itself without the moxml gem:

    rake validate            # identity: the cases match the moxml export (tools/validate.rb)
    rake schema              # every row against schema/test.schema.json (tools/validate_schema.rb)
    rake all                 # both

CI (`.github/workflows/validate.yml`) runs the structure gate on every
push/PR with plain ruby, and the identity gate against lutaml/moxml@main.

Status: SCHEMA VALIDATION PASS (177 rows, 7 families); IDENTITY PASS
(177 cases match the moxml reference export).

## Consumers

Every moxml implementation consumes this corpus as its conformance suite
through the vendored-pin chain: a dataset revision ships as a moxml
release, the Rust crate re-vendors it at its next release
(`tests/data/`), and the TS package pins both wasm bundles and the
dataset. The reference implementation exercises the corpus through its
own conformance specs, regenerated by `rake conformance:export`.

Point the tooling at a non-sibling checkout with `MOXML_PATH`.
